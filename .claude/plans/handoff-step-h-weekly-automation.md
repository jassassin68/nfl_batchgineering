## Step H scope

### H1. Weekly recommendation schedule

Dagster schedule that materializes `weekly_bet_recommendations` early
Thursday morning Eastern Time (the typical NFL slate-release rhythm:
schedule firm by Wednesday, sharp money starts hitting Thursday).

- Cron: `0 6 * * 4` (Thursday 6 AM ET) or similar.
- Skip weeks: if there are no upcoming games (offseason, bye-week
  scenarios), the asset already handles this gracefully -- but the
  schedule should know to not bother firing during the offseason
  (April-August). Use a partition or a sensor gate on
  `mart_upcoming_game_predictions` row count.
- Tied to: current season config -- a `season_config.yml` or env var
  the user updates each summer to point at the new season.

Mirror the pattern in `dagster_project/schedules/weekly_schedule.py`
(which already exists for predictions).

### H2. Notification sink

When `weekly_bet_recommendations` materializes, the user needs to know
*what to bet* without opening Dagster. Three options in increasing
order of investment:

1. **Markdown file in a watched directory**. Simplest. Dagster already
   writes `reports/recommendations/recs_*.md`. Add a symlink or copy
   to a fixed path like `reports/CURRENT_WEEK.md` that's easy to open.
2. **Email**. SMTP from the asset's success hook. Requires SMTP creds
   in `.env`. Plain-text MIME with the markdown body inlined.
3. **Slack / Discord**. Webhook URL in `.env`, formatted message with
   the bet table and key metrics.

Recommend (1) + (3): markdown for archive, Slack for push-notification
on the user's phone. Skip email -- nobody reads weekend email in time.

### H3. Closing-line snapshot schedule

Triggered from Step E's closing-line capture asset. New schedules:

- Sunday 12:55 PM ET (5 min before main slate) -- covers all 1 PM
  games.
- Sunday 3:55 PM ET -- covers 4 PM and 4:25 games.
- Sunday 7:55 PM ET -- covers SNF.
- Thursday 7:55 PM ET, Monday 7:55 PM ET, Saturday afternoons during
  the late-season Saturday slate.

These are deliberately separate schedules, not one cron job, so a
failure in one window doesn't drop snapshots for another window.

### H4. Post-game reconciliation schedule

Tuesday early-morning materialization of Step E's reconciliation asset
once all weekend games are final (early Tuesday catches MNF results).

Cron: `0 5 * * 2` (Tuesday 5 AM ET).

### H5. Health-check / failure alerting

Every scheduled run that fails MUST notify the user, not just sit in
the Dagster run history.

- Dagster sensor that watches for failed runs of any of the H1-H4
  schedules in the last 24h and pushes a notification via the same
  Slack webhook as H2.
- Heartbeat: a daily "all clear" notification at 9 AM ET that
  summarizes the last 24h of scheduled-job state. Absence of
  heartbeat = absence of system = also bad. The user should miss the
  heartbeat if it stops.
- `risk_events` from Step G should also feed this sensor -- any new
  `event_type='anomaly_blocked'` row pushes immediately, not on the
  daily heartbeat.

### H6. Operational dashboard (markdown, not a UI)

Single `reports/STATUS.md` regenerated by a daily Dagster asset that
shows:

- Current bankroll (from G1's `BANKROLL_LEDGER`).
- This week's recommendations (link to current week's report).
- Last week's results (W/L, ROI, CLV avg).
- Season-to-date metrics from `mart_bet_performance`.
- Last 7 days of `risk_events`.
- Last successful run of each H1-H4 schedule.

Cheap. Reads from existing marts. No webserver, no auth, just a
markdown file the user opens to see the state of the world.

### H7. Tests

- `tests/test_schedules.py` -- each schedule's cron expression
  evaluates to the intended local time; offseason gate fires when
  expected.
- `tests/test_notifications.py` -- formatting of Slack message,
  markdown report symlink behavior. Mock the actual webhook.
- `tests/test_status_report.py` -- STATUS.md renders correctly on a
  synthetic state.

## Project conventions (non-negotiable)

Same as Steps A-G. Specifically:

- **Loud failure**: any unhandled exception in a scheduled job must
  surface to the user within 1 hour. No silent failures.
- **Observable**: every scheduled run writes a row somewhere
  (Dagster's run log is fine for v1) that proves it executed.
- **Idempotent**: re-running a scheduled job for the same week must
  not double-record bets or double-settle bankroll.
- **No webhook secrets in code or markdown**. Slack/Discord webhook
  URLs go in `.env`, gitignored.
- **Timezone discipline**: all crons in Eastern Time (NFL operates
  on ET). Document the timezone the Dagster instance is running in.

## Critical files to read first

- `dagster_project/schedules/weekly_schedule.py` -- existing pattern.
- `dagster_project/__init__.py` -- where new schedules register.

- Step E's closing-line and reconciliation assets -- H3, H4.

## Out of scope for Step H (deferred)

- A real web UI. Markdown reports + Slack push is enough for a
  one-person operation.
- Mobile app, SMS alerts, paging integrations.
- Cross-region failover, HA Dagster. Single-instance is fine.
- Auto-betting through a sportsbook API. The user still manually
  places bets through their book; automation only covers
  recommendation production and tracking.
